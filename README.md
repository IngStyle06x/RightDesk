# RightDesk

# Техническое задание на разработку системы «RightDesk»

## 1. Предмет задания
Исполнитель разрабатывает демонстрационную веб-систему приёма обращений граждан в МВД с автоматическим определением подразделения и срочности обращения (далее модуль ИИ). Система является тестовой, не подключается к реальным системам МВД и использует только вымышленные данные.

## 2. Цель
Показать, что автоматическое распределение обращений по подразделениям и выявление срочных случаев сокращает ошибки маршрутизации и риск потери срочных обращений.

## 3. Пользователи и права доступа
Вход выполняется по логину и паролю. Система различает два типа пользователей.

**3.1. Гражданин**
- самостоятельно регистрируется в системе;
- отправляет обращения;
- видит только свои обращения, их статусы и ответы сотрудников.

**3.2. Сотрудник МВД**
- учётную запись создаёт Исполнитель, самостоятельная регистрация невозможна;
- закреплён за одним подразделением и видит только его обращения;
- принимает обращения в работу, отвечает на них, закрывает их;
- передаёт обращение в другое подразделение, если модуль ИИ определил подразделение неверно.

## 4. Порядок обработки обращения
1. Гражданин отправляет текст обращения.
2. Модуль ИИ определяет подразделение, признак срочности и уровень уверенности.
3. Обращение попадает в список определённого подразделения.
4. Если уверенность ниже 60%, обращение попадает в подразделение «Канцелярия» для ручного распределения.
5. Сотрудник принимает обращение в работу, при необходимости передаёт его другому подразделению, затем пишет ответ.
6. Гражданин видит ответ и статус в личном кабинете.
7. Каждое действие по обращению (кто, что, когда) сохраняется в истории обращения.

**Статусы обращения:** новое, требует проверки, в работе, получен ответ, закрыто.

## 5. Подразделения
Модуль ИИ распределяет обращения по семи подразделениям:

1. Полиция общей юрисдикции: кражи, хулиганство, шум, бытовые конфликты.
2. ГИБДД: аварии, штрафы, нарушения ПДД.
3. Миграция и документы: паспорт, регистрация, иностранные граждане.
4. Киберполиция и мошенничество: звонки «из банка», фишинг, взлом аккаунтов.
5. Экономическая безопасность и противодействие коррупции: взятки, хищения, подделка документов.
6. Жалобы на действия сотрудников: нарушения со стороны сотрудников МВД.
7. Прочее: обращения, не относящиеся к компетенции МВД.

Дополнительное подразделение «Канцелярия» модулем ИИ не определяется, обращения попадают туда автоматически по правилу из п. 4.

**Срочными** считаются обращения, содержащие угрозу жизни или здоровью, насилие, сообщение о пропавшем человеке, преступление в процессе совершения.

## 6. Требования к интерфейсу
Система работает в браузере. Оформление минималистичное, без декоративных элементов.

**6.1. Общие страницы:** вход, регистрация гражданина.

**6.2. Кабинет гражданина:**
- форма отправки обращения (текст от 20 до 5000 символов);
- список обращений со статусами;
- просмотр ответов сотрудников;
- для срочных обращений заметное сообщение: при угрозе жизни звонить 112.

**6.3. Кабинет сотрудника:**
- список обращений подразделения с фильтрами по срочности, статусу и дате;
- срочные обращения расположены выше остальных и выделены цветом;
- карточка обращения: текст, подразделение, срочность, уверенность модуля ИИ, три наиболее вероятных подразделения, история действий;
- действия: «Принять в работу», «Передать в другое подразделение», «Ответить», «Закрыть»;
- страница сводки: количество обращений по статусам, доля срочных, доля обращений, исправленных сотрудниками.

**6.4.** На страницах регистрации и отправки обращения отображается предупреждение: «Система тестовая, не вводите реальные личные данные».

## 7. Требования к модулю ИИ
7.1. Модуль обучается Исполнителем специально для этого проекта. Использование готовой модели без обучения на собственных данных не допускается.

7.2. Для обучения Исполнитель формирует набор размеченных обращений. Реальные обращения не используются. Источники: тексты, написанные вручную, тексты по шаблонам, открытые тексты жалоб.

7.3. Объём набора: не менее 200 примеров на каждое из семи подразделений и не менее 300 срочных примеров. Каждый пример содержит текст, подразделение и признак срочности.

7.4. Все личные данные в примерах (ФИО, адреса, телефоны, номера документов) вымышленные или заменены масками.

7.5. Набор делится на три части: обучение (70%), проверка в ходе разработки (15%), итоговая проверка (15%). Итоговая часть не используется при обучении и подборе параметров.

7.6. Исполнитель сравнивает не менее двух разных моделей и подключает ту, у которой лучшие показатели качества.

7.7. Исправления подразделения, внесённые сотрудниками, сохраняются в базе для последующего дообучения.

7.8. Время обработки одного обращения не более 1 секунды на обычном компьютере.

## 8. Требования к качеству
Проверка выполняется на итоговой части набора (п. 7.5):

| Показатель | Требование |
|---|---|
| Доля верно определённых подразделений (accuracy) | не ниже 85% |
| Средняя точность по подразделениям (macro-F1) | не ниже 0.80 |
| Доля найденных срочных обращений (recall) | не ниже 90% |

Приоритет у показателя срочности: пропуск срочного обращения недопустим чаще, чем ошибочная пометка обычного обращения как срочного.

Исполнитель предоставляет отчёт с таблицей показателей по каждому подразделению и таблицей ошибок (какие подразделения модель путает между собой).

## 9. Тестовая база данных
9.1. База данных имитирует базу МВД и содержит:
- подразделения;
- сотрудников (должность, звание, подразделение);
- граждан;
- обращения;
- историю действий по обращениям;
- ответы сотрудников;
- исправления подразделений.

9.2. Объём тестовых данных: не менее 20 сотрудников, 100 граждан, 1000 обращений в разных статусах, с ответами и историей.

9.3. Все данные вымышленные и создаются автоматически одной командой. Команда позволяет полностью сбросить и заново заполнить базу.

9.4. Исполнитель создаёт готовые тестовые аккаунты: не менее одного гражданина и по одному сотруднику в каждом подразделении. Логины и пароли передаются Заказчику.

## 10. Требования к безопасности
10.1. Пароли хранятся только в защищённом (хешированном) виде.

10.2. Без входа в систему доступ к обращениям закрыт.

10.3. Гражданин видит только свои обращения, сотрудник только обращения своего подразделения. Права проверяются на стороне сервера.

10.4. Текст обращений выводится на страницах в безопасном виде (защита от внедрения кода).

10.5. Окончательное решение по обращению принимает сотрудник, модуль ИИ даёт только рекомендацию.

## 11. Не входит в задание
- подключение к реальным системам МВД;
- мобильное приложение;
- отправка писем, СМС и уведомлений;
- обработка реальных персональных данных.

## 12. Состав результатов работы
1. Работающая система, запускаемая на обычном компьютере.
2. Тестовая база данных и команда её заполнения.
3. Обученная модель и набор данных, на котором она обучалась.
4. Отчёт о качестве модуля ИИ (раздел 8).
5. Инструкция: запуск системы, вход, пересоздание тестовых данных.
6. Исходный код в репозитории на GitHub.

## 13. Порядок приёмки
Система принимается, если выполнены все условия:
1. Гражданин регистрируется, отправляет обращение, видит статус и ответ.
2. Сотрудник видит только обращения своего подразделения и выполняет действия «принять», «передать», «ответить», «закрыть».
3. Срочные обращения выделены и расположены первыми.
4. Обращения с уверенностью ниже 60% попадают в «Канцелярию».
5. Показатели качества соответствуют разделу 8.
6. Система запускается по инструкции Исполнителя без его участия.
